# Dagsverk configuration names and upgrades

External server, OAuth-service, Compose and Synology configuration uses the
`DAGSVERK_*` prefix. Replace the `TIMEKEEPER_` prefix with `DAGSVERK_` while keeping
the suffix, for example `DAGSVERK_PUBLIC_ORIGIN`, `DAGSVERK_CONNECT_ORIGIN`,
`DAGSVERK_CONNECT_ENCRYPTION_KEY` and `DAGSVERK_SERVER_DB_PASSWORD_FILE`.
New package templates and setup tools write the new names. During 2.x,
container templates also supply identical legacy aliases so automatic rollback
to a pre-migration server image retains its configuration. Administrators set
only the Dagsverk names; the templates keep the container aliases together.

Legacy `TIMEKEEPER_*` aliases remain supported through Dagsverk 2.x. When both
names are supplied, `DAGSVERK_*` wins. Conflicting values produce a diagnostic
containing only setting names; never their values. No removal is scheduled in
2.x; removal requires a later major version, release notes and an explicit
migration notice. Existing files are not silently rewritten and secrets are
not regenerated by this rename.

1. Retain the existing private configuration and encrypted instance backup.
2. Rename operator environment keys, keeping values and file permissions intact.
   Old Compose `.env` files and existing standalone/service environments continue
   to work during this transition. New Compose templates map the legacy aliases
   into the new container names. Do not set differing aliases intentionally.
3. Restart affected processes. Verify About, database connectivity and
   **Administration → Internet accounts → Check setup**. The existing saved
   configuration remains effective; environment changes do not overwrite centrally
   persisted administration settings. Change provider registrations through
   Administration, then restart. General authentication/settings recovery
   deliberately preserves provider settings and secrets.
   Complete the upgrade on every replica before configuring the newly editable
   Microsoft registration. Existing four-field provider settings retain their
   shape while Microsoft settings are unchanged. Older binaries cannot read the
   additional Microsoft fields after that feature is used; retain the pre-upgrade
   configuration backup for a downgrade across that boundary.
4. Verify backup/restore and provider reconnect with the same original secrets.
   Changing the managed service encryption key is unrelated to a variable rename
   and cannot preserve its existing grants.

The internal `timekeeper.*` Java/property keys, persisted settings/secret fields,
JDBC identities, API headers, Synology package IDs, volume paths and archive
formats are unchanged. Existing `application.properties` registration files and
instance backups remain readable. CI test harness variables and historical
verification records retain their original names; they are not operator settings.

For direct OAuth setup see [direct registration](SHARED-SIGN-IN.md#direct).
For managed deployment see [managed OAuth](SHARED-SIGN-IN.md#managed).
