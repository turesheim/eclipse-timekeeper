# Dagsverk configuration names and upgrades

External server, OAuth-service, Compose and Synology configuration uses the
`DAGSVERK_*` prefix. Replace the `TIMEKEEPER_` prefix with `DAGSVERK_` while keeping
the suffix, for example `DAGSVERK_PUBLIC_ORIGIN`, `DAGSVERK_CONNECT_ORIGIN`,
`DAGSVERK_CONNECT_ENCRYPTION_KEY` and `DAGSVERK_SERVER_DB_PASSWORD_FILE`.
New package templates and setup tools write the new names. During 2.x,
container templates also supply identical legacy aliases so automatic rollback
to a pre-migration server image retains its configuration. Administrators set
only the Dagsverk names; the templates keep the container aliases together.

Legacy `TIMEKEEPER_*` aliases remain supported through Dagsverk 2.x. When both
names are supplied, `DAGSVERK_*` wins. Conflicting values produce a diagnostic
containing only setting names; never their values. No removal is scheduled in
2.x; removal requires a later major version, release notes and an explicit
migration notice. Existing files are not silently rewritten and secrets are
not regenerated by this rename.

1. Retain the existing private configuration and encrypted instance backup.
2. Rename operator environment keys, keeping values and file permissions intact.
   Old Compose `.env` files and existing standalone/service environments continue
   to work during this transition. New Compose templates map the legacy aliases
   into the new container names. Do not set differing aliases intentionally.
3. Restart affected processes. Verify About, database connectivity and
   **Administration → Internet accounts → Refresh setup status**. The existing saved
   configuration remains effective; environment changes do not overwrite centrally
   persisted administration settings. For provider registration changes, follow
   [OAuth application setup](SHARED-SIGN-IN.md). General authentication/settings recovery
   deliberately preserves provider settings and secrets.
   Complete the upgrade on every replica before configuring the newly editable
   Microsoft registration. Existing four-field provider settings retain their
   shape while Microsoft settings are unchanged. Older binaries cannot read the
   additional Microsoft fields after that feature is used; retain the pre-upgrade
   configuration backup for a downgrade across that boundary.
4. Verify backup/restore and provider reconnect with the same original secrets.
   Changing the managed service encryption key is unrelated to a variable rename
   and cannot preserve its existing grants.

The internal `timekeeper.*` Java/property keys, persisted settings/secret fields,
JDBC identities, API headers, Synology package IDs, volume paths and archive
formats are unchanged. Existing `application.properties` registration files and
instance backups remain readable. CI test harness variables and historical
verification records retain their original names; they are not operator settings.

For direct OAuth setup see [direct registration](SHARED-SIGN-IN.md#direct).
For managed service deployment see [OAuth service operations](CONNECT-SERVICE.md).

## Retain operator settings


For environment-based first setup, use `DAGSVERK_CONNECT_SHARED=false`,
`DAGSVERK_PUBLIC_ORIGIN`, `DAGSVERK_GOOGLE_TASKS_CLIENT_ID`,
`DAGSVERK_GOOGLE_TASKS_CLIENT_SECRET`, `DAGSVERK_MICROSOFT_TASKS_CLIENT_ID`
and `DAGSVERK_MICROSOFT_TASKS_CLIENT_SECRET`. Settings saved in Administration
take precedence over these first-boot defaults.

Existing operator setups can use a Java properties file with only the configured
providers:

```properties
timekeeper.tasks.google.client-id=REPLACE_WITH_CLIENT_ID
timekeeper.tasks.google.client-secret=REPLACE_WITH_CLIENT_SECRET
timekeeper.tasks.microsoft.client-id=REPLACE_WITH_CLIENT_ID
timekeeper.tasks.microsoft.client-secret=REPLACE_WITH_CLIENT_SECRET
```

These server app registrations are separate from each account's OAuth grant.
Preserve Java properties escaping for any backslashes in values. Keep filled
settings outside source control, browser code and Compose environment fields.

For the **Synology package**, edit the retained
`/var/packages/timekeeper/var/server/secrets/task_providers.properties` as an
operator, then restart Dagsverk in Package Center. Startup copies it into the
protected, read-only container mount. Edit the retained file, rather than its
generated copy under `target/private`. Upgrades preserve it. Native and Hyper
Backup application archives include it with a verified checksum. Restoring an
older archive without it clears destination app registrations; configure them
and reconnect as needed. Actual Package Center and Hyper Backup repository
restore still require [NAS acceptance](SYNOLOGY-PACKAGE.md).

For the **Compose distribution**, run `python3 setup.py` from `server/deploy`
after updating deployment files. It preserves existing credentials and creates
a comment-only `<state>/secrets/task-providers/application.properties`. Edit it,
retain the enclosing `secrets` directory's private permissions, and acquire the
updated mount:

```sh
docker compose up -d --force-recreate --wait api-1 api-2
```

Only the task-provider directory is mounted into the API replicas. Logical
`backup.sh`/`restore.sh` retains it; older backups restore without app
registrations. The host `secrets` parent remains private; mounted files are
readable by the container's application user.

For a **standalone Java server**, load the properties file through
`QUARKUS_CONFIG_LOCATIONS=file:/absolute/path/to/task-providers.properties`, or
set `DAGSVERK_GOOGLE_TASKS_CLIENT_ID`, `DAGSVERK_GOOGLE_TASKS_CLIENT_SECRET`,
`DAGSVERK_MICROSOFT_TASKS_CLIENT_ID` and
`DAGSVERK_MICROSOFT_TASKS_CLIENT_SECRET` in its protected service environment.
Restart after changes. Set `DAGSVERK_PUBLIC_ORIGIN` to the external HTTPS
origin unless central service settings already provide it.
